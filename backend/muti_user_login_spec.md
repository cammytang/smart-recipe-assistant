# 智能菜谱助手：多用户登录与画像面板实施规范

## 0. 文档信息

| 项目 | 内容 |
| --- | --- |
| 功能 | 前端注册、登录、退出、画像查看与清空 |
| 版本 | v1.1 |
| 状态 | 设计已确认，前端待实现 |
| 实施范围 | 对接已有接口，不新增后端业务能力 |

本文供 AI 编码助手和开发者实现前端使用。应先检查现有页面和接口代码，保留聊天规划、方案确认、菜谱步骤及购物清单功能。仅在收到实施指令后修改代码。

## 1. 当前能力与本期目标

### 1.1 已有能力

- 后端提供注册、登录、查询当前用户和退出接口。
- 认证采用 PostgreSQL 服务端 Session 和 HttpOnly Cookie，不使用 JWT。
- 已有 `users`、`user_sessions`、`user_memories` 三张表。
- 记忆与菜单接口已要求有效会话，长期记忆按 user_id 隔离。
- 未实现对话历史持久化、菜谱收藏和画像标签直接编辑接口。

接口依据：[认证文档](docs/AUTH_API.md)、[记忆与菜单文档](docs/MEMORY_API.md)。如实际接口与本文不一致，应报告差异，不凭空编造接口。

### 1.2 本期流程

游客浏览和输入需求 → 首次发送时打开登录弹窗 → 登录成功后继续规划 → 查看或清空个人画像 → 退出并清理页面数据。

- 游客可以浏览首页、输入文字和选择示例，不调用受保护的 AI 接口。
- 用户首次发送或点击示例触发规划时，需要登录。
- 登录使用弹窗，用户无需离开当前页面。
- 登录后，两页顶部均提供头像入口，右侧抽屉展示个人画像和退出按钮。
- 不提供匿名生成、头像上传、第三方登录、账号切换器、找回密码、菜谱收藏或画像直接编辑。
- 即使不做账号切换器，也必须处理 A 退出后 B 在同一浏览器登录的数据隔离。

## 2. 技术和 API 约定

### 2.1 前端结构

使用现有 React、React Router 和页面样式体系。用户状态通过 React Context 管理，不新增 Redux。

建议组件与职责：

| 文件/组件 | 职责 |
| --- | --- |
| `auth/AuthProvider.jsx` | 用户状态、恢复会话、登录/注册/退出协调、身份版本 |
| `auth/AuthDialog.jsx` | 登录与注册弹窗，表单状态局部保存 |
| `auth/UserMenu.jsx` | 两页共用的登录/头像入口 |
| `auth/ProfileDrawer.jsx` | 画像加载、展示、清空确认和退出 |
| `api/client.js` | 统一地址、credentials、错误解析和取消请求 |
| 现有页面及 App | 挂载 Provider，接入动作拦截与身份清理 |

可按项目现有目录调整，不要求 TypeScript 迁移。

### 2.2 接口映射

| 方法与路径 | 用途 | 成功响应 |
| --- | --- | --- |
| `POST /api/v1/users` | 注册 | 201，用户信息，不自动登录 |
| `POST /api/v1/sessions` | 登录 | 201，`user`、`expires_at`；设置 Cookie |
| `GET /api/v1/users/me` | 恢复/核实会话 | 200，`id`、`username` |
| `DELETE /api/v1/sessions/current` | 退出 | 204，无响应体 |
| `GET /memory` | 读取画像 | 200，`memory`、`memory_summary` |
| `POST /memory/clear` | 清空全部长期记忆 | 200，清空后的记忆 |
| `POST /memory/confirm` | 确认菜单、提取偏好 | 200，更新后的记忆 |
| `POST /menu/plan` | 规划菜单 | 200，方案与记忆摘要 |
| `POST /menu/stream` | 生成详细菜谱 | SSE 流 |

认证路径和业务路径的前缀不同，不能统一给所有请求追加 `/api/v1`。

### 2.3 Cookie 与请求配置

- 所有认证和业务 fetch 请求均使用 `credentials: 'include'`，包括菜单 SSE 的 fetch。
- 不在 localStorage/sessionStorage 保存密码、会话凭证、长期画像或跨用户聊天数据。
- 不尝试用 JavaScript 读取/删除 HttpOnly Cookie；退出由后端清除 Cookie。
- API 地址集中配置，例如 `VITE_API_BASE_URL`；本地前后端统一使用 localhost，或统一使用 127.0.0.1。
- 写请求必须匹配后端允许的 Origin；浏览器自动发送 Origin，不在前端手动构造。
- 如使用开发代理，应明确前缀转发规则，并验证认证 Cookie 和业务路径均能正常访问。
- 生产使用 HTTPS，Cookie Secure 由后端配置；不得为方便前端而关闭后端鉴权或来源校验。
- 204 响应不调用 `response.json()`；SSE 不走普通 JSON 响应解析。

## 3. 用户状态与启动恢复

全局状态建议：

```ts
type AuthStatus = 'checking' | 'anonymous' | 'authenticated' | 'error';

type User = { id: string; username: string };

type AuthState = {
  status: AuthStatus;
  user: User | null;
  authEpoch: number;
};
```

`authEpoch` 用于区分身份有效期；每次身份失效、退出或账号变化时更新。异步响应提交状态前必须确认请求捕获的用户 ID 和 authEpoch 仍匹配。

页面启动调用 `/api/v1/users/me`：

| 结果 | 行为 |
| --- | --- |
| 请求中 | 首页可以输入；顶部显示检查状态，禁止提前发起业务请求 |
| 200 | 设置当前用户，按需加载画像 |
| 401 | 进入游客状态，不自动弹登录框 |
| 网络错误/5xx | 显示“暂时无法确认登录状态”和重试入口，不假定未登录 |

checking 期间点击发送可以暂存一次意图；检查成功后继续，确认未登录后弹窗。error 状态先提示重试，不提交请求或丢弃输入。

同一时刻只允许一个登录弹窗。并发多个 401 不能反复打开弹窗或覆盖待执行意图。

## 4. 首页入口与游客行为

- 游客顶部右侧显示“登录”，保留现有“新建对话”功能。
- 已登录显示圆形头像，可使用用户名首字母或默认用户图标；不依赖不存在的头像接口。
- 游客输入内容保留在当前页面内存中，不写入任何用户画像。
- 点击发送或示例时，保存该次需求并打开登录弹窗，暂不添加“AI 正在规划”状态，也不发送 `/menu/plan`。
- 取消登录后保留输入，但取消自动恢复意图；用户需要再次点击发送。
- 文案使用“登录后，为你规划菜谱并记住饮食偏好”，不承诺已有菜谱收藏或云端聊天历史。

## 5. 登录与注册弹窗

### 5.1 登录

内容：用户名、密码、显示/隐藏密码按钮、登录按钮、注册入口、关闭按钮和错误提示。

- 用户名按后端规则去首尾空白并转小写，规范化后 3～64 位字母、数字或下划线。
- 密码遵循当前后端：8～128 个可打印 ASCII 字符，允许空格，不 trim、不转大小写；不接受中文和控制字符。
- 使用 `autocomplete="username"`、`autocomplete="current-password"`。
- 支持回车提交；请求中禁用重复提交。
- 401 显示“用户名或密码错误”，留在弹窗，不触发全局会话过期流程。
- 422 显示输入校验提示；429 依据 Retry-After 提示稍后再试；网络/服务错误提供重试。
- 成功后清除局部密码状态、关闭弹窗、显示头像，并执行第 6 节的恢复规则。
- 关闭时清理密码。请求已发送后关闭/取消不能被视为服务端登录必然取消：丢弃自动恢复意图，并在请求结束或下一次操作前通过 `/me` 重新核实身份。

### 5.2 注册

在同一个弹窗中切换注册视图，不堆叠两个弹窗。字段为用户名、密码、确认密码，密码使用 `autocomplete="new-password"`。

- 两次密码一致后提交，只发送 username、password。
- 201 后切回登录视图，填入用户名并清空密码，提示“注册成功，请登录”。不假定注册已设置 Cookie。
- 409 提示用户名已被使用；其余错误按登录的分类处理。
- 切换登录/注册视图保留用户名和游客待发送需求，不保留密码。

### 5.3 无障碍与移动端

- 弹窗有可读标题、输入标签和错误关联；错误通过 aria-live 提示。
- 打开时管理焦点，Tab 不移出模态区域；关闭后焦点回到触发按钮或输入框。
- 支持 Escape 关闭，并遵守待执行意图的取消规则。
- 手机键盘弹出时，输入项、错误和提交按钮可滚动访问。

## 6. 登录后恢复操作

使用结构化 pendingIntent，不保存任意回调闭包或任意 URL：

```ts
type PendingIntent = {
  id: string;
  kind: 'plan' | 'confirm';
  ownerUserId: string | null;
  payload: unknown; // 实施时定义为对应的需求/方案快照类型
};
```

- 每次只保存一个明确的待执行动作，禁止因重复点击建立多个任务。
- 游客输入的 `plan` 意图 ownerUserId 为 null，首次成功登录后允许执行一次。
- 登录前属于 A 的动作必须标记 ownerUserId=A。重新登录为 A 时才允许恢复；登录为 B 时丢弃该动作及 A 的页面数据。
- 自动消费意图前先清除待执行标记并设置执行锁，避免 React effect 重跑、重复渲染或连续点击造成重复请求。
- 登录成功不能既调用发送函数，又通过 effect 再调用一次。
- 用户取消弹窗、退出或新建对话时取消待执行意图。
- 只对明确被 401 拒绝、尚未执行业务的操作允许恢复。网络中断/超时的 POST 不自动重放，因为后端可能已经执行。
- 画像清空不自动恢复或重放，重新登录后需要用户再次确认。
- SSE 连接失败、生成中断或会话失效时，不自动重新生成整套菜单；重新登录后提供显式“重新生成”操作。

## 7. 用户画像抽屉

两页共用头像入口；点击后从右侧展开，移动端可使用全屏抽屉。

### 7.1 内容

- 用户名、默认头像。
- 饮食偏好：`diet_preferences`。
- 过敏/忌口：`allergies`。
- 不喜欢的食材：`disliked_ingredients`。
- 常用食材：`favorite_ingredients`。
- 常见用餐人数：`common_serving_size`，兼容 null、整数和旧字符串。
- 最近确认菜品：`recent_dishes`；不得称为完整历史或已做过的菜。
- 其他已有偏好：`rejected_patterns`，有数据时展示。
- 最后更新时间、清空记忆按钮、退出登录按钮。

首次打开加载 `GET /memory`，展示 loading、空状态、成功状态、失败重试。空数组显示“暂无记录”。画像是标签展示，不提供单项增删编辑控件。

确认菜单成功后同步响应中的画像，或将画像缓存标记为待刷新；不得让抽屉永久显示旧偏好。

### 7.2 清空记忆

点击后在抽屉内显示明确确认：“清空全部长期偏好？此操作不会删除账号。”

- 确认后调用 `POST /memory/clear`，期间禁用重复提交。
- 成功后以服务端返回内容刷新画像。
- 失败时保留原画像并显示错误，不提前显示清空成功。
- 清空记忆不同时清空当前菜谱或删除账号。
- 清空后用户再次确认菜单可能重新记录偏好，应在说明中明确。

## 8. 退出与账号数据隔离

### 8.1 主动退出

1. 用户点击退出，进入退出中状态，阻止新增业务请求。
2. 中止当前业务请求/SSE，并使旧响应版本失效。
3. 调用 `DELETE /api/v1/sessions/current`。
4. 成功 204 后清空用户、画像、聊天、方案、菜谱、购物清单和勾选状态；关闭抽屉及弹窗，取消 pendingIntent。
5. 返回首页游客状态；清理/隔离 React Router 的历史 state，浏览器后退不能恢复旧账号的菜谱。

退出失败时提示“退出失败，请重试”，不能宣称服务端会话已经撤销。保留可重试的账户入口；已中止的生成任务不自动恢复。

### 8.2 会话过期与其他标签页

- 业务请求 401 时，使身份版本失效，停止业务请求并隐藏旧用户私有内容，仅在内存隔离区暂存允许恢复的该用户动作。
- 登录为同一用户后按第 6 节恢复；登录为另一用户时销毁旧用户数据。
- 旧请求即使在 AbortController.abort 后返回，也必须通过 userId/authEpoch 检查才能更新页面。
- 可使用 BroadcastChannel 通知同源标签页发生登录/退出变化；消息不携带密码或会话凭证，接收方调用 `/me` 核实当前身份。
- 页面重新获得焦点时重新核实会话，并避免重叠检查。发现用户 ID 变化时清理旧用户数据，禁止把旧动作提交给新用户。
- 后端鉴权在 SSE 请求开始时执行；退出不保证服务器即时停止已启动生成。前端必须停止读取与展示旧流。

## 9. 第二页的访问规则

- 打开 `/menu-progress` 时先确认登录状态，再启动生成流。
- 未登录时不消费路由中的菜谱数据、不发生成请求；展示登录入口或返回首页。
- 路由中传递的菜谱状态必须带 ownerUserId，并与当前用户比较。
- ownerUserId 不匹配、缺少方案或直接打开地址时，回到首页提示重新规划。
- checking/error 期间不启动流；刷新恢复后也不能因认证 effect 重跑而重复启动同一任务。
- 当前没有后端持久化任务恢复接口，无法确定任务状态时提供显式重新生成，不承诺断点续传。

## 10. 验收标准

1. 游客可以输入；首次发送弹登录框，登录前不调用菜单规划接口。
2. 关闭登录框保留输入；再次主动登录不会恢复已取消的动作。
3. 注册成功回到登录，用户名已填入，密码已清空。
4. 登录成功只规划一次，重复点击/React effect 重跑不会重复提交。
5. 刷新后 `/me` 恢复用户；加载中不闪出错误的登录状态。
6. `/me` 网络错误或 503 提供重试，不错误地判断为游客。
7. 多个业务 401 只出现一个登录弹窗；登录接口自身的 401 只显示表单错误。
8. 画像显示当前用户实际数据，空状态和失败重试正常，无未实现的编辑/收藏按钮。
9. 清空画像成功后刷新；清空失败时保留原数据；重登后不自动清空。
10. 退出成功撤销服务端会话，清理两页所有用户数据和待执行动作。
11. 退出失败有明确提示，不能假报成功。
12. A 退出后 B 登录，B 页面不展示 A 的聊天、画像、方案、勾选和购物清单；后退也不能恢复。
13. A 的迟到响应或 SSE 数据不能更新 B 的页面。
14. 其他同源标签页退出或变更身份后，当前页能重新核实并清理旧数据。
15. 第二页没有会话、没有方案或 ownerUserId 不匹配时不启动生成流。
16. 全部需要认证的请求携带 Cookie，正常运行的后端 Origin 校验未被关闭。
17. 弹窗/抽屉支持键盘操作、焦点恢复与手机键盘场景。
18. 跑通真实后端链路：注册 → 登录 → 规划 → 确认 → 生成 → 查看画像 → 清空 → 退出。模拟测试与真实联调结果分别报告。
